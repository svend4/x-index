# Конвейер вики x-index

Документ описывает, как вики собирается, проверяется, индексируется и отдаётся агентам и людям. Он разделяет два состояния: что уже реализовано в репозитории и что описано как следующий шаг. Разбор проблемы, сравнение подходов и рекомендации — в [ANALYSIS.md](ANALYSIS.md).

## 1. Слои данных

Вики построена как LLM-вики: сырые источники, поддерживаемые карточки и правила. Здесь к этому добавлен второй уровень, потому что реестров слишком много, чтобы каждую строку делать карточкой.

| Слой | Где лежит | Что в нём | Кто пишет | В git |
|---|---|---|---|---|
| Сырые источники | `wiki/raw/` | снимки реестров и инвентарь сессии с датой | скрипт или ручная выгрузка | да, компактные снимки; постраничные файлы — нет |
| Карточки, уровень 1 | `wiki/cards/<кластер>/<id>.md` | README-карточка на инструмент: факты, оценки, источники | агенты и люди по `SCHEMA.md` | да |
| Строки каталога, уровень 2 | `wiki/.index/wiki.sqlite`, таблица `entries` | каждая запись реестра как строка с полями и FTS | скрипт `index` | нет, пересобирается |
| Правила и словарь | `wiki/SCHEMA.md`, `wiki/taxonomy.json` | схема карточки, классы данных, кластеры | человек | да |
| Производные | `wiki/INDEX.md`, `wiki/clusters/`, `wiki/catalog.json`, `wiki/queue/` | оглавления, каталог карточек, очередь заданий | скрипт `build`, `queue` | да |

Почему два уровня. Карточка — дорогая единица знания: её пишут и проверяют. Строка каталога — дешёвая: факты из API без текста. Из строки можно поднять карточку по запросу или по приоритету. Так вики не превращается в свалку из тысяч пустых файлов.

Для каждой стадии условие завершения одно: результат проверен командой из таблицы, а не ответом агента.

## 3. Роли агентов и очередь

- **Harvester** (стадии 1, 1а): только выгрузка и снимок. Агент не интерпретирует данные.
- **Classifier** (стадия 3а): получает запись и таксономию, возвращает кластер, группу и уверенность. Низкая уверенность уходит человеку на выборку.
- **Enricher** (стадия 6): один агент на один батч карточек. Получает только выдержки источников, которые ему передал конвейер, и промпт из `queue/ENRICH_PROMPT.md`. Агент не ходит в интернет сам, пока не появится явный шаг с сохранением выдержки в `raw/`.
- **Grounder** (стадии 7а и 7б): скрипт, не модель. Проверяет, что каждый факт опирается на существующий источник и что цитата есть в тексте источника.
- **Adversary** (стадия 8): модель большего класса, которой поручено найти слабые места в мнениях и фактах. Она не добавляет факты.
- **Owner** (стадия 9): владелец вики. Решения «Тест / Позже / Нет» принимает он, а не агенты.

Очередь: `enrich-queue.jsonl` содержит по строке на карточку: номер, батч, приоритет, `id`, путь, кластер, вид. Приоритеты:

1. позиции из инвентаря сессии (сразу полезны владельцу);
2. MCP-серверы с удалённой точкой подключения;
3. прочие MCP-серверы;
4. остальное.

Размер батча по умолчанию 20. Агент берёт батч целиком и не трогает чужие батчи, поэтому конфликтов в git почти не будет.

Ограничения на расход. Перед запуском батчей задаётся бюджет токенов и число карточек за прогон. Прогон останавливается при превышении бюджета или при росте числа ошибок проверок выше порога (например, 10 % батча).

## 4. Контроль качества

Главный риск вики, которую пишут модели, — правдоподобные, но не подтверждённые факты. Защита строится в несколько слоёв:

1. **Структура.** `lint` проверяет поля, перечисления, даты, разделы, ссылки и токены. Ошибка блокирует сборку.
2. **Источники.** Каждый факт помечен номером источника. Номер без источника — ошибка (стадия 7а).
3. **Цитаты.** Фрагменты из источника, на которые опирается карточка, должны дословно присутствовать в тексте выдержки (стадия 7б). Это самая сильная проверка: её нельзя обойти правдоподобным текстом.
4. **Разделение фактов и мнений.** Разделы «Чем выделяется» и «Когда не подходит» помечены как мнение. Мнение не может стать `verified`.
5. **Статусы.** `verified` ставит только сверка с первоисточником и дата сверки. Через 180 дней lint предупреждает о повторной сверке.
6. **Защита от инъекций.** Тексты источников — данные. Промпт запрещает выполнять указания из текста источника, а найденные указания фиксируются в карточке как риск.
7. **Выборка человека.** 5–10 % карточек каждого прогона читает владелец. Если ошибки в выборке выше порога, прогон возвращается на доработку, а правила уточняются.

Метрики качества для набора карточек: доля карточек без ошибок `lint`; доля фактов с проверяемой цитатой; доля мнений, помеченных как мнение; доля карточек с датой сверки моложе 180 дней.

## 5. Поиск по Markdown: варианты и выбор

Цель поиска — отвечать на вопросы вида «что подключить для X», «что умеет Y», «чем Z отличается от W», «какие бесплатные без ключа», и при этом указывать источник.

| Подход | Сильные стороны | Слабые стороны | Когда уместен |
|---|---|---|---|
| grep / ripgrep по Markdown | ноль зависимостей, точные совпадения | нет ранжирования, плохо с синонимами и падежами | быстрая проверка, до 200 файлов |
| BM25 через SQLite FTS5 | встроен в Python, быстрый, ранжирование, префиксный поиск | не понимает синонимы и другие языки, падежи нужно учитывать вручную | ядро поиска; имена продуктов и коды (XRechnung, SGB IX) ищутся хорошо |
| Плотные эмбеддинги (многоязычные) | синонимы, перефразы, RU/EN/DE в одном пространстве | слабее на точных идентификаторах; нужна модель и пересчёт при смене модели | второй канал для гибридного поиска |
| Гибрид BM25 + эмбеддинги с RRF | лучшее из двух, устойчив к разным формулировкам | два индекса, немного сложнее | рекомендуемая схема, когда в корпусе больше нескольких сотен карточек |
| Перегенерация вопроса и переписывание запроса | решает неудачные формулировки пользователя | дополнительный вызов модели, риск сдвига смысла | трудные запросы, после первого промаха |
| Фильтры по полям (SQL) | точные ответы на вопросы о свойствах: цена, класс данных, хостинг, язык | требует заполненных полей | всегда, сначала фильтр, потом текст |
| Граф ссылок (``wikilinks``, теги) | дешёвый граф связей без экстракции сущностей | зависит от качества ссылок | раскрытие соседних карточек («что ещё похоже») |
| GraphRAG (извлечение графа сущностей) | глобальные вопросы по корпусу | дорого, шумно, сложно поддерживать | не нужен на этом масштабе |
| Длинный контекст (всё в промпт) | просто | 60 000 записей не влезут, качество падает на длинных входах | только для одного кластера из 20–40 карточек |
| Дообучение модели на вики | теоретически точнее | дорого, устаревает при каждом обновлении | не рекомендуется |

**Рекомендуемый конвейер запроса (гибрид):**

```
вопрос пользователя
  → разбор: язык, домен, фильтры (кластер, класс данных, цена, хостинг, статус)
  → фильтры по полям (SQL)                                  [точные свойства]
  → BM25 по FTS5 (заголовок, теги, сводка, тело)            [имена, коды, термины]
  → плотный поиск по эмбеддингам (опционально)              [синонимы, перефразы]
  → слияние RRF, top-50
  → переранжирование (кросс-энкодер или малая модель), top-10
  → раскрытие соседей по ссылкам (1 шаг)                    [контекст]
  → ответ: только по найденным карточкам, со ссылками на id и путь,
           с явным «данных нет» при пустом результате
```

Правила нарезки. Карточка короче 2 000 токенов — один фрагмент. Длиннее — делим по разделам `##`, и каждый фрагмент получает префикс: название, кластер, вид, статус. Такой префикс повышает точность поиска (это приём «контекстного поиска», который описан, в частности, в публикациях Anthropic 2024 года; эффект на вашем корпусе надо измерить).

Правила ответа. Ответ опирается только на найденные карточки. Каждое утверждение сопровождается `id` карточки. Если результат пуст или слабый, ответ так и говорит, а не домысливает. Мнения из раздела «Чем выделяется» отделяются от фактов.

## 6. Рекомендуемые сочетания

| Вариант | Состав | Когда выбирать | Стоимость и сложность |
|---|---|---|---|
| A. Минимальный (уже реализован) | Markdown + YAML frontmatter, SQLite FTS5, `tools/wiki.py`, git | до нескольких тысяч строк; нужна работа офлайн; нужна прозрачность | ноль зависимостей, один скрипт |
| B. Гибрид | A + эмбеддинги (многоязычная модель, локально или через API) в SQLite (`sqlite-vec`) или в файле NumPy + RRF | когда BM25 промахивается на перефразах, а в корпусе сотни карточек | одна модель, пересчёт векторов раз в снимок |
| C. С переранжированием | B + переранжирование кросс-энкодером на top-50 | когда важна точность первых трёх результатов | ещё одна модель; заметная задержка, но приемлемая |
| D. Для агентов | A/B/C + MCP-сервер с инструментами `wiki_search`, `wiki_get`, `wiki_compare`, `wiki_facets` | когда вики должна работать внутри Claude и других агентов | сервер на Python по шаблону skill `mcp-builder` |
| E. Для людей | A + Obsidian (lint по скиллу `obsidian-notes`) или статический сайт (MkDocs / Docusaurus) из карточек | когда нужны навигация, графы и поиск в браузере | сборка сайта, без серверной части |
| F. Фреймворки (LlamaIndex, LangChain) | любой из вариантов выше через адаптер | когда нужны готовые коннекторы к внешним источникам, а не только к файлам | лишний слой абстракции; для этого корпуса не нужны |

Мнение: сочетание A → D решает большую часть задач владельца. B и C добавлять только после того, как оценка (раздел 7) покажет промахи BM25. Фреймворки и векторная база данных на отдельном сервере на корпусе в десятки тысяч строк не окупаются.

## 7. Оценка

1. **Эталонный набор.** 100–200 пар «вопрос → ожидаемые карточки и факты». Вопросы берутся из практики владельца, а не придумываются. Для каждого вопроса фиксируется, что ответ обязан содержать и чего не должен содержать.
2. **Метрики.** Recall@10 по карточкам; MRR; точность цитат (есть ли `id` и совпадает ли факт с карточкой); доля правильных отказов («данных нет»); задержка.
3. **Прогон.** Каждый раз после пересборки индекса. Регрессия по любой метрике блокирует публикацию индекса.
4. **Сравнение вариантов.** A против B и C по одному и тому же набору. Решение о переходе принимается по цифрам.

## 8. Стоимость и время

Оценка порядка величины, без привязки к ценам конкретного поставщика. Цены моделей меняются, поэтому их берут из актуального прайса.

- **Стадии без моделей** (выгрузка, нормализация, заготовки, индекс, lint): ноль токенов, минуты на тысячи записей.
- **Классификация малой моделью**: около 300–500 входных токенов на запись (название, описание, таксономия в кэше). Для 60 000 записей это порядка 20–30 млн входных токенов. Проще классифицировать только карточки и выборку каталога.
- **Обогащение карточки**: около 4 000–6 000 входных токенов (выдержки источников и промпт; промпт можно кэшировать) и 800–1 200 выходных на карточку.
  - 1 500 карточек: около 8 млн входных и 1,5 млн выходных токенов.
  - 10 000 карточек: около 50 млн входных и 10 млн выходных токенов. Такой объём — это пакетная работа в несколько прогонов, а не одна сессия.
- **Проверки** (ссылки, цитаты) — скрипты, без токенов. Состязательная проверка — примерно треть стоимости обогащения, если делать её на всех карточках; разумнее на выборке и на карточках с мнениями о рисках.

Мнение: полный охват 60 000 записей карточками не нужен. Карточки нужны для 300–1 500 инструментов из практики владельца и для того, что он реально спрашивает. Остальное живёт строками каталога и поднимается в карточку по запросу (отложенное обогащение). Это снижает стоимость в десятки раз.

## 9. Риски и меры

| Риск | Последствие | Мера |
|---|---|---|
| Выдуманные факты | неверные решения о подключении | цитаты из выдержек (7б), статусы, выборка человека |
| Инъекции из описаний | агент выполнит чужие указания | тексты источников — данные; промпт; фиксация указаний в карточке |
| Устаревание | карточка описывает старую версию | `verified_on`, предупреждения lint, ежемесячный снимок и diff |
| Дубли и семейства | одна функция в десяти записях | идентификаторы, список семейств, поле `group` и `tags` с синонимами |
| Персональные данные в карточках | утечка | запрет в схеме, поиск по шаблонам, проверка выборкой |
| Юридические и лицензионные ограничения | нарушение условий источника | только публичные API и явные экспорты; учёт условий; ссылка на источник в каждой записи |
| Рост стоимости | неконтролируемые расходы | бюджет прогона, лимит карточек, отложенное обогащение |

## 10. Дорожная карта

1. **Готово.** Схема, таксономия, инструмент `tools/wiki.py`, инвентарь сессии, выгрузка реестра MCP, рукописные карточки для инструментов сессии, индекс FTS5, поиск из терминала, очередь и промпт обогащения.
2. **Следующий шаг (1–2 дня работы).** Прогон обогащения для 40–60 карточек из инвентаря сессии, затем lint и выборка владельца. Добавить проверки 7а и 7б.
3. **Оценочный набор (1 день).** 100 вопросов из практики владельца, метрики, базовый замер BM25.
4. **Эмбеддинги (если замер покажет промахи).** Вариант B, затем C.
5. **MCP-сервер для агентов.** Инструменты поиска, получения карточки, сравнения и фасетов. Это превращает вики в инструмент, который Claude использует напрямую.
6. **Масштабирование.** Классификация каталога, отложенное обогащение по запросам, ежемесячный снимок с отчётом об изменениях.
