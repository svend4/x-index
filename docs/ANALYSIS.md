Основа: данные этой среды (ответы `ListConnectors`, `ListSkills`, системные уведомления о статусе серверов, списки инструментов), публичный реестр MCP (61 245 серверов), выборка каталога Make (3 записи), файлы `SKILL.md` локальных плагинов. ## 1. Итог

1. **Проблема не в нехватке описаний.** Описаний много, но они разбросаны по источникам без общего ключа. Часть пустая: у 12 из 35 коннекторов аккаунта описания в каталоге нет. Часть написана маркетингом. И нет слоя «подходит / не подходит», привязанного к классу данных, юрисдикции, цене и хостингу.
2. **Нужны два слоя.** Первый — дешёвые строки каталога для всех записей. Второй — карточки-README для нескольких сотен инструментов из практики владельца. Остальные записи поднимаются в карточку по запросу.
3. **Источник правды — Markdown с YAML-шапкой в git.** Производные файлы (SQLite FTS5, JSON-каталог, оглавления) пересобираются скриптом. Эмбеддинги, переранжирование и MCP-сервер добавляются тогда, когда замер покажет, что они нужны.
4. **Что уже работает в репозитории:** схема карточки, таксономия из 26 кластеров с группами, инструмент `tools/wiki.py` на стандартной библиотеке Python, выгрузка официального реестра MCP, 1 607 карточек: 107 карточек инвентаря сессии обогащены выдержками и проверены в нескольких кругах (статус `draft`), 1 500 заготовок реестра; индекс, поиск и замер на 93 вопросах (hit@10 0.80).
5. **Чего нет:** обогащения 1 500 заготовок реестра (очередь готова, запусков не было), векторного индекса (промахи замера — перефразы и немецкие запросы, раздел 7.1), MCP-сервера для агентов. Полное обогащение 60 000 записей не рекомендую: это дорого и не даёт качества (раздел 9).

## 2. Где лежат описания возможностей

«10 000 возможностей» из вопроса — это не один каталог. В этой среде видно несколько источников разного типа.

| Источник | Что содержит | Как получить | Объём в этой среде | Качество описаний | Ограничения |
|---|---|---|---|---|---|
| Каталог Claude (skills, коннекторы, плагины) | карточки: название, описание, источник («от Anthropic», партнёр, сообщество), число установок | веб-интерфейс claude.ai, поиск по каталогу | по данным скилла `ecosystem-curator`: около 10 000 позиций в 57 категориях (со слов автора скилла, не проверено) | неоднородное: есть пустые описания и маркетинг | выгрузки нет; категория показывает 70–80 позиций; поиск без «Показать все» обрезает выдачу |
| Инструменты сессии: `ListConnectors`, `ListSkills`, `ListPlugins` | состояние подключения и описание для каждой позиции аккаунта | вызов инструмента из сессии | 35 коннекторов, 39 скиллов, плагинов в аккаунте нет | 12 из 35 коннекторов без описания | только то, что подключено или включено в аккаунте |
| Поиск из сессии: `SearchMcpRegistry`, `SuggestConnectors`, `SearchSkills` | результаты поиска и карточки установки | инструменты сессии | зависит от запроса | те же, что в каталоге | не выгружает весь каталог |
| Официальный реестр MCP (`registry.modelcontextprotocol.io`) | сервер: имя, описание, версия, удалённые точки подключения, ссылка на репозиторий, дата публикации | открытый API без ключа; страницы по 100 записей, курсор вида `имя:версия` | 61 245 серверов (последняя версия), из них 60 281 активных и 964 устаревших | описания заявлены авторами; у 99 % активных серверов описание длиннее 20 знаков | не содержит списка инструментов и возможностей; много экспериментальных записей |
| Каталог Make (`apps_list`, инструмент MCP) | приложения: техническое имя, отображаемое название, описание, версия | постранично, до пустой страницы; общего счётчика нет | выборка из 3 записей; полный объём не измерен | короткие описания; часть на других языках; поле `keywords` пустое в выборке | нет категорий; внутреннее имя не совпадает с названием (`a3dcart` — Shift4Shop) |
| npm (поиск пакетов) | пакеты, загрузки за месяц, ключевые слова | открытый API поиска, проверен доступ | выборка из 2 пакетов, один с ~2 млн загрузок в месяц | популярность, а не качество | пакет не равен коннектору |
| Zapier, IFTTT, n8n и другие | каталоги интеграций на сайтах | веб-страницы | не выгружались | не проверено | условия использования сайтов; проверить до выгрузки |
| Локальные `SKILL.md` | инструкции; поле `description` — триггер срабатывания | файлы плагинов | прочитано 3 файла (`ecosystem-curator`, `vault`, `obsidian-notes`) | точное, но короткое | знает только установленное |
| Исходный код коннекторов (GitHub) | точное описание возможностей | репозитории | не читалось: доступ сессии ограничен репозиторием `svend4/x-index` | высокое, если поддерживается | нужен подключённый репозиторий |

Что из этого следует:

- Для точности нужны и каталог (что доступно), и первоисточник (что делает). Описание в каталоге — гипотеза, которую проверяет проба.
- Официальный реестр MCP — самый удобный для массовой выгрузки источник. Но он открытый: там и сильные серверы, и эксперименты, и дубли. Без фильтров он бесполезен для выбора.
- Каталоги Make и Zapier массово выгружаются только через API аккаунта (для Make — токен, который нужно настроить) или через постраничный обход. Проверить условия до начала.

## 3. Как комбинировать коннекторы, скиллы и плагины

Удобно думать о трёх типах слоёв:

- **Коннектор** — доступ. Он даёт инструменты, которые читают и меняют внешние данные (почта, документы, базы, сервисы).
- **Скилл** — метод. Это инструкция, как решать задачу: порядок шагов, критерии, шаблоны, правила безопасности.
- **Плагин** — упаковка. Это набор скиллов и команд, иногда с коннектором внутри.

Инструменты дают руки, скилл — порядок работы. Плагин собирает их в пакет. Для одной функции нужен один основной путь и один проверяющий. Остальные — альтернативы для пробы.

Сочетания, которые видны в этой среде:

1. **Немецкое социальное право.** Процесс ведёт `legal-domain-manager` (или `sozialrecht-sachsen`). Источники дают три базы: `lulius` (федеральное право и калькуляторы сроков), `nu-legal` (право земель и ЕС, граф решений), `zitierfest` (официальный текст и проверка цитат). Результат проверяет плагин `verification-foundation`. Порядок: поиск нормы → проверка цитаты → черновик → состязательный разбор.
2. **Электронные счета.** `normapi-einvoices` проверяет и разбирает XRechnung и ZUGFeRD по правилам KoSIT. Исходные данные берутся из файлов (скиллы `xlsx`, `pdf`), отправка — через Gmail по явной команде владельца.
3. **Документы.** Коннекторы Google Docs, Sheets, Slides, Drive. Скилл `google-workspace` задаёт правила правки, `docs` создаёт документ, `doc-coauthoring` задаёт процесс.
4. **Вики и заметки.** `obsidian-notes` проверяет ссылки и индексы, `vault-anything` генерирует вики из кода и файлов `raw/`, а эта вики хранит каталог инструментов.
5. **Автоматизация.** `make-com` строит сценарии и проверяет конфигурации. `workflow-automation` выполняет цепочки внутри диалога, `samautomation-workflows` проверяет сценарии n8n.
6. **Память и перенос контекста.** Здесь перекрытие сильнее всего (раздел 5). Нужен один основной путь.

Правило: одну функцию обслуживает не больше двух источников одного типа (основной и проверяющий). Всё остальное — кандидат на выключение.

## 4. Что подходит, а что нет

Критерий отбора уже есть в скилле `ecosystem-curator`: шкала 0–14 по семи пунктам, классы данных A, B, C. Вики добавляет к нему поля, по которым шкала считается: класс данных, цена, способ входа, хостинг, юрисдикция, рекомендация куратора.

Порядок отсева:

1. **Жёсткие ограничения.** Чужая юрисдикция для практики в ФРГ — «Нет». Класс B (документы, в том числе с данными подопечных) без договора обработки и понятного хостинга — «Позже». Класс C (запись в системы) — только с подтверждением для каждого действия. Платное — после пробы бесплатных аналогов.
2. **Мягкие критерии.** Релевантность задачам владельца, зрелость (репозиторий, версии, установки), пересечение с уже работающим.
3. **Решение.** Его принимает владелец и записывает в свой реестр решений. Вики хранит факты и рекомендацию.

Предварительная оценка по шкале (не решение владельца):

| Позиция | Оценка | Основание |
|---|---|---|
| `lulius`, `nu-legal`, `zitierfest` | Тест | право ФРГ, класс A, nu:legal без ключа и бесплатно, пересечение: земельное право покрыто только nu:legal и Zitierfest |
| `legal-data-hunter` | Тест с оговоркой | многоюрисдикционная база; в описаниях расходятся числа — уточнить |
| CourtListener, Descrybe, Midpage (американские базы) | Нет | юрисдикция: 0 по шкале |
| `ifttt` | Нет | потребительский уровень, не связан с практикой |
| `tinyfish` | Позже | класс C (вход в личные кабинеты, отправка форм), оплата через кошелёк, нужны условия сайтов |
| `make-com` | Тест | уже подключён, класс C с подтверждениями, зона аккаунта EU (по наблюдению) |
| `zapier` | Позже | две записи каталога, ни одна не подключена; сначала устранить дубль |
| `gmail`, `google-calendar`, `google-drive` | Тест | уже подключены; запись только с подтверждением |

| Статусы меняются | в сессии: 9 плагин-серверов требуют авторизации, 4 не подключились, 2 подключены (системные уведомления) | карточка устаревает за часы | поле `status` в инвентаре и повторный снимок |

Отдельно о перекосе. Открытый реестр MCP в основном состоит из инструментов для разработки. Это наблюдение из эвристики, а не точный подсчёт, но оно важно: на юридические, медицинские и бухгалтерские инструменты приходится доля порядка единиц процентов. Поэтому отбор кандидатов должен идти по приоритетным кластерам владельца, а не по общему рейтингу.

## 6. Вики: почему Markdown и как устроена карточка

### 6.1. Варианты хранения

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| Markdown с YAML-шапкой в git | читается человеком и моделью; diff и история; рендерится на GitHub и в Obsidian; переносится | нет типизированных запросов; таблицы плохо масштабируются; конфликты при параллельной работе | **основа** |
| Только JSON или YAML | типизация, фильтры | плохо для нарратива, больше токенов, неудобно читать | как производный каталог |
| Notion или Confluence как вики | интерфейс, совместная работа | лимиты API, слабая история версий, привязка к сервису, массовые правки неудобны | для людей, но не как источник правды |
| Векторная база без структуры | масштабирование | теряет поля, сложно объяснить ответ, лишняя инфраструктура | добавлять как индекс, не как хранилище |
| Таблица (Sheets) как каталог | понятные фильтры | плохо для текста и мнений | допустимо для строк каталога |

Мнение: нужен гибрид форматов. Карточка — Markdown, потому что в ней есть рассуждения, мнения и ссылки. Свойства для фильтров — в YAML-шапке, а из шапки строятся JSON и SQLite. Так факты и нарратив не смешиваются, и фильтр работает без модели.

### 6.2. Что внутри карточки

- **Шапка (YAML).** Факты и флаги: `kind`, `cluster`, `status`, `data_class`, `price`, `auth`, `hosting`, `jurisdiction`, `source_urls`, `snapshot`, `verified_on`, `curator_hint`. Все строки в JSON-форме, поэтому файл одновременно валиден и как YAML.
- **Разделы.** «Суть», «Для чего», «Возможности», «Чем выделяется», «Ограничения и риски», «Когда не подходит», «Альтернативы», «Источники», «Заявлено автором». Порядок фиксирован, чтобы любой агент находил нужное.
- **Три уровня доверия.** Факт — с номером источника. Мнение — помечено словом «Мнение». Заявление — дословная цитата автора в кавычках. Так читатель сразу видит, что проверено, а что нет.

### 6.3. Схема «LLM-вики» по Карпати в этом проекте

- **Сырой слой** (`wiki/raw/`) — снимки источников с датой, неизменяемые. Здесь реестр MCP и инвентарь сессии.
- **Вики** (`wiki/cards/`) — карточки, которые поддерживают агенты и человек по правилам.
- **Схема** (`wiki/SCHEMA.md`, `wiki/taxonomy.json`) — правила, которые читают и люди, и агенты.
- **Операции.** Ingest: снимок → заготовки → очередь → обогащение → проверка. Query: поиск по индексу с цитатами. Lint: проверка схемы, ссылок, сроков сверки.
- **Оглавление и журнал.** `wiki/INDEX.md` — вход в вики, `wiki/log.md` — хронология изменений.

Схема вики в проекте повторяет идею «знание накапливается, а не выводится заново при каждом вопросе». Это главное отличие от классического RAG, который каждый раз собирает ответ из кусков.

### 6.4. Почему не «10 000 карточек сразу»

- Карточка — дорогая единица: её нужно читать, проверять и поддерживать. Пустые или поверхностные карточки хуже их отсутствия: они создают ложное ощущение покрытия.
- Большинство записей реестра никогда не понадобится владельцу. Их достаточно хранить строками каталога и находить поиском.
- Устаревание: описание инструмента меняется, карточка должна обновляться. Для тысяч карточек это отдельная работа, которая не окупается.

## 7. Поиск по Markdown: RAG

### 7.1. Что уже проверено

Инструмент `ask` работает поверх SQLite FTS5 с BM25 и фильтрами по полям. Индекс из 1 607 карточек и 61 245 строк каталога собирается за 2,5 секунды. Восемь тестовых запросов из практики показали:

- Для запросов с именем продукта или кодом (`XRechnung`, `Gmail`, `Notion`, `AI Act`, `make`, `Obsidian`) первая карточка релевантна во всех восьми случаях. Это оценка по здравому смыслу, не эталонный замер.
- Для запроса «Widerspruch Bescheid Frist» в топ-3 попали три правовых скилла, а из каталога — релевантная по смыслу запись (`bescheid-vorlage-lint-kag`).
- Для запросов с общими словами («страницы», «риск») каталог возвращает шум: «Табуля», «Супермаркет САМПО», «ИИПодпись». Поэтому в выводе каждый результат помечен: «все слова» или «часть слов». Читатель сразу видит слабые совпадения.

Вывод: для имён и кодов BM25 достаточен. Для синонимов, перефразов и разных языков нужны эмбеддинги. Решать, нужны ли они, должен эталонный набор, а не мнение.

Замер на наборе из 93 вопросов (2026-11-10, режим fallback, k = 10): hit@10 0.80, recall@10 0.72, MRR 0.66; нежелательная карточка в топ-3 у 18 % вопросов. Режим AND без ранжирования на естественном языке почти ничего не находит (hit@10 0.11). Промахи — немецкие запросы к английским и русским описаниям, перефразы без общих слов и ссылки на нормы со знаком § (подробности — в [PIPELINE.md](PIPELINE.md), раздел 7).

### 7.2. Варианты и выбор

Сравнение подходов (подробнее в [PIPELINE.md](PIPELINE.md), раздел 5):

- **grep** — ноль зависимостей, но нет ранжирования; годится до нескольких сотен файлов.
- **BM25 (FTS5)** — быстро, ранжирует, хорошо с именами; слабо с синонимами.
- **Эмбеддинги** — синонимы и перефразы; слабее на точных кодах; требуют модели и пересчёта при её смене.
- **Гибрид BM25 + эмбеддинги с RRF** — лучший баланс, когда корпус растёт.
- **Фильтры по полям** — обязательны для вопросов вида «бесплатный, без ключа, с хостингом в ЕС». Текстовый поиск здесь ненадёжен, нужен SQL.
- **Граф ссылок** — дешёвая замена GraphRAG: ``wikilinks`` и теги дают соседей карточки.
- **GraphRAG** с извлечением сущностей — дорого и шумно, на этом масштабе не окупается.
- **Всё в один промпт** — 60 000 строк не влезут; даже кластер из 40 карточек даёт заметную цену и теряет точность.
- **Дообучение** — дорого, устаревает при каждом обновлении. Не рекомендую.

### 7.3. Рекомендуемый конвейер запроса

```
вопрос
  → разбор: язык, домен, фильтры (кластер, класс данных, цена, хостинг, статус)
  → фильтры по полям (SQL)                       [точные свойства]
  → BM25 по FTS5                                 [имена, коды, термины]
  → эмбеддинги (по замеру)                       [синонимы, перефразы]
  → слияние RRF, top-50
  → переранжирование, top-10                     [точность первых мест]
  → соседи по ссылкам, один шаг                  [контекст]
  → ответ только по найденным карточкам, со ссылками на id и путь;
    при пустом или слабом результате — «данных нет»
```

Правила, которые стоит соблюдать с первого дня:

- карточку короче 2 000 токенов индексировать целиком; длиннее делить по разделам `##`, и каждому фрагменту добавлять префикс с названием, кластером, видом и статусом. Публикация Anthropic о контекстном поиске (2024) сообщала о заметном снижении ошибок извлечения при таком подходе; на вашем корпусе эффект надо измерить;
- эмбеддинги хранить вместе с идентификатором модели, чтобы менять модель без потери данных;
- тексты из реестров и описаний — недоверенные данные. Ответ не выполняет указаний из них, а найденные указания фиксируется в карточке как риск;
- ответ обязан ссылаться на `id`. Утверждения-мнения отделять от фактов.

### 7.4. Рекомендуемые сочетания

| Вариант | Состав | Когда | Сложность |
|---|---|---|---|
| A (уже есть) | Markdown + YAML, SQLite FTS5, `tools/wiki.py`, git | до нескольких тысяч строк; нужна офлайн-работа и прозрачность | ноль зависимостей |
| B | A + эмбеддинги в SQLite (`sqlite-vec`) или в файле NumPy + RRF | BM25 промахивается на перефразах | одна модель |
| C | B + переранжирование на top-50 | важна точность первых трёх мест | ещё одна модель |
| D | A/B/C + MCP-сервер с инструментами `wiki_search`, `wiki_get`, `wiki_compare`, `wiki_facets` | вики должна работать внутри Claude и других агентов | сервер по шаблону скилла `mcp-builder` |
| E | A + Obsidian (проверка ссылок скиллом `obsidian-notes`) или статический сайт (MkDocs, Docusaurus) | людям нужны навигация и граф | сборка сайта |
| F | LlamaIndex или LangChain поверх любого варианта | нужны готовые коннекторы к внешним источникам | лишний слой; для этого корпуса не нужен |

Мнение: A → D решает большую часть задач владельца. B и C добавлять только по замеру. Фреймворки и отдельный сервер векторной базы для корпуса в десятки тысяч строк не окупаются.

## 10. Мнение и рекомендации

1. **Не строить вики на все 60 000 записей.** Строки каталога — на все записи. Карточки — на 300–1 500 инструментов из практики владельца. Остальное — отложенное обогащение по запросу: запрос поднимает строку в карточку, карточка кэшируется.
2. **Приоритет по домену владельца.** В репозитории приоритетными помечены 12 кластеров: мета-инструменты, почта, документы, автоматизация, право ФРГ и ЕС, право других юрисдикций, медицина, счета, память, комплаенс, файлы и хранилища, встречи и транскрипция. Это предположение по установленным скиллам и коннекторам. Его нужно подтвердить.
3. **Разделить знание и решения.** Вики хранит факты и мнения об инструментах. Решения «Тест / Позже / Нет» — в реестре владельца (`ECOSYSTEM-REGISTRY.md`). Связывать их по `id`.
4. **Проверять факты по источнику, а не по уверенности модели.** Цитата из выдержки — единственная надёжная защита. Мнения помечать. Статус `verified` ставить только после сверки.
5. **Не доверять описаниям, особенно маркетинговым.** Описание — гипотеза, проба — факт. Это правило из скилла `ecosystem-curator`, и оно верно и для вики.
6. **Сначала эталонный набор, потом эмбеддинги.** Сто вопросов из практики владельца покажут, нужен ли векторный поиск и насколько он поможет. Без набора выбор инструмента основан на вкусе.
7. **Ежемесячный снимок и diff.** Список изменений в реестрах (появились, исчезли, сменили статус, сменили описание) — самый дешёвый способ держать вики актуальной.
8. **MCP-сервер для вики.** Это лучший способ, чтобы агенты, включая Claude, пользовались базой. Инструменты: поиск, карточка по `id`, сравнение двух-трёх карточек, фасеты по полям.
9. **Make: выгружать каталог скриптом с токеном.** Постраничный обход через MCP-инструмент дорог по контексту: каждая страница занимает место в диалоге. Перед этим проверить документацию Make о доступе к API.
10. **Глубину брать из первоисточника.** Для коннекторов это инструкции сервера, документация поставщика и SKILL.md. Чужие репозитории читать только после подключения.
11. **Проверять правовые скиллы по текстам норм до использования для дат.** Сверка карточки расчёта сроков с текстами §§ BGB, SGG, SGB X и SGB I нашла в скилле ошибку в расчёте по дням, неверную ссылку в почтовом примере и предел Wiedereinsetzung, противоречащий тексту. Такой скилл нельзя считать надёжным по описанию.
12. **Сверить соседние правовые скиллы.** Плагин sozialrecht-sachsen содержит сходные правила сроков (Bekanntgabe, Wiedereinsetzung) и пока не сверен по текстам норм; сверка — следующий шаг.
